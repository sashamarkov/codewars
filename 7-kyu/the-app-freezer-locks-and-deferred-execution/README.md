<h2><a href=https://www.codewars.com/kata/69f17bc82c1ad736dbe44bf9/train/csharp target="_blank">The App Freezer: Locks and Deferred Execution</a></h2><h3>7 kyu</h3><h3 id="the-educational-challenge">The Educational Challenge</h3><p>In enterprise C#, developers use <code>lock</code> statements to protect in-memory caches from race conditions. However, <strong>Deferred Execution</strong> (LINQ and <code>yield return</code>) can accidentally cause locks to be held for massive amounts of time, completely freezing the application!</p><p><strong>Trap 1: Data Coming In (<code>IQueryable</code>)</strong>If you evaluate an <code>IQueryable</code> (like calling <code>.ToList()</code>) <em>inside</em> a lock, the lock remains closed while the application waits for the SQL database to respond over the network. </p><p><strong>Trap 2: Data Going Out (<code>yield return</code>)</strong>If you read from your cache using <code>yield return</code> <em>inside</em> a lock, the compiler pauses the method. The lock remains physically held open while the caller iterates over the data! If the caller does a slow <code>foreach</code> loop, your entire application freezes!</p><h3 id="your-task-the-puzzle">Your Task (The Puzzle)</h3><p>Look at the <code>UserCache</code> class. It has two severe bottlenecks. Refactor both <code>Refresh()</code> and <code>GetUsers()</code> so that:</p><ol><li>The database I/O happens <em>outside</em> the lock.</li><li>The caller can safely iterate over the cached users without holding the lock open.</li><li>The cache's internal <code>List&lt;User&gt;</code> remains perfectly thread-safe from Race Conditions.</li></ol>
